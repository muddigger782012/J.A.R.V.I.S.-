# Read-only capability request feasibility review

`review capability request` plus an exact saved description inspects the private request list, then produces a bounded definition for supported media-volume, numeric timer, exact installed-app and updater requests. App targets must be uniquely resolved and launchable at review time. The definition separates its human action, prerequisites, verification method and a new explicit command that the user may choose to issue. Reviewing creates no approval or outcome session, launches no action, saves no learning and does not mark the request complete.

Absolute volume parsing takes priority over relative volume aliases, including maximum-volume wording. Timers use the existing 1–86400-second validation; percentage targets are 0–100 and nearest-supported-level. Missing or ambiguous apps do not receive a bound executable definition. Unresolved timer durations request details. Other wording is outside this review's current scope, not proof the whole app lacks the feature: an existing routine, clearer parameters or further implementation review may cover it.

Definitions are generated locally from existing validated parsers and host app lookup, not cloud text or the broad planned-domain catalogue. Request lookup is canonical-exact and read-only. Review replies are not added to AI history/context. The request stays in its unverified backlog; no new capability is generated, tested or deployed by review. Read-only review preserves pending app/timer outcome checks and their expiry, but cannot approve them. Review controls are reserved against aliases.
