# Explicit offline command teaching

Teach one existing handler without cloud AI: “Teach Jarvis that coffee break means start a timer for 5 minutes”, “Teach Jarvis that browse desk means open Chrome”, or “Teach Jarvis that desk level means set media volume to 25%”. Names are short non-reserved phrases; durations are numeric seconds/minutes/hours from 1 second to 24 hours. App targets require a unique exact installed launcher label. One-off teaching does not accept multi-action workflows, shell code, calls or arbitrary capabilities; approved routines remain the mechanism for compositions.

The host previews the bound target and asks yes/no. Approval alone never teaches an app or timer. After its request, the same persisted outcome session retains the alias; only an accepted “it worked” result permits saving. Media-volume teaching uses device readback verification before saving. No, unrelated input, expiry, failed launch/readback, or failed outcome prevents learning. The approval or feedback words are not aliases. No AI request is needed to plan these teaching instructions.

Explicit teaching is consent to save a verified lesson even when automatic AI learning is disabled. Pending stores persist a scoped explicitTeaching flag; it cannot be combined with non-learnable/replayed/contextual device sessions or unsupported volume lessons. Old pending JSON defaults to automatic behavior. Existing learned command/intent names and routines are checked before preview; forget the old definition before explicitly reteaching a name. Existing relative-volume/time/updater teaching keeps its behavior.

Tests cover strict single-target resolution, name/parameter boundaries, uniqueness, persisted approval/outcome separation, explicit-vs-automatic consent, cancellation/failure and original-alias storage. Local theme/whitespace and Android CI checks are separate from phone tests.
