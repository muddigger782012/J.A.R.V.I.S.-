# Repository context in Developer Home coding replies

Home's existing **Ask Jarvis / save instructions** action now reads relevant authorized source before sending a coding request to the selected Gemini or OpenAI model. Choose Developer or Personal in the existing application selector and describe the problem with concrete terms. No additional API key, model-selection or approval mechanism is introduced.

Developer source is read from `feature/jarvis-developer`; Personal source is read from `main`, in `muddigger782012/J.A.R.V.I.S.-`. Each request resolves a branch once, validates its commit and tree, and reads content at the immutable commit SHA. Returned file paths, sizes and Git blob hashes must match the inventory. A branch moving after inventory cannot mix later source into that request. The reply's provenance identifies the actual revision; it is not a statement about subsequent branch changes.

The existing Kotlin `RepositoryIntelligence.Reader` and `RepositoryAnalysis` perform retrieval and lexical relevance analysis. Home uses a narrower budget: at most eight relevant allowlisted files and 400,000 advertised source bytes. Only matching product source and canonical shared integration source are candidates. Documentation, arbitrary repositories, credential/signing files, symlinks, binaries and Gradle configuration are not sent through this path. Existing manual repository browsing and patch-preview policies are unchanged.

At most four planned files contribute two excerpts each. Every excerpt includes its path, blob SHA and line range; the context includes the repository, branch, product and commit SHA. Excerpts are limited to seven lines and 2,400 UTF-8 bytes each. The entire serialized context, including JSON escaping, must fit 20,000 bytes. The existing provider request limit remains 64,000 bytes. These are excerpts and lexical estimates, not whole-repository or compilation verification.

Whole-file sanitation precedes excerpt slicing so an excerpt beginning inside a multiline credential cannot reveal its continuation. It removes named credential values, common token formats, private-key blocks, secret XML resources/manifest entries, authorization values, URL passwords and the configured provider/GitHub credentials. Control and directional characters are filtered. The existing read allowlist remains the primary restriction; sanitation cannot establish that every arbitrary string in a repository is non-sensitive.

The owner request and repository JSON are separate text parts in both providers' native request formats. A fixed system policy treats all repository strings, comments and fields as untrusted evidence, never instructions or authorization. Repository content never becomes a system instruction. Models receive no execution tools. Patch generation and exact-diff review still use the existing workbench and require fresh explicit approval before a write.

If source access, relevance, revision validation or the context budget fails, the model receives an explicit `unavailable` context and must answer from the instruction text only. Home labels that reply **Repository context unavailable**. It does not claim the source was inspected. A cancellation stops both source retrieval and the subsequent AI request; it does not silently fall back to the cloud. Missing AI credentials keep the existing offline instruction-saving behavior without a source or provider call.

Saved replies include only provenance and the reply text. Retrieved source, GitHub credentials and approval state are not added to project persistence. Existing cancellation, interruption recovery, request receipts and stale-callback rejection remain active. No automatic source commit, merge, build, production signing, publication or installation is performed by a Home coding reply.

Regression coverage includes recorded GET-to-analyzer-to-provider payloads for both services, product isolation, secret exclusion, multiline redaction, source/task/revision binding, failed reads, cancellation, Unicode/escaping budgets, real Android widget integration, and native Home provenance/fallback. Controlled provider fixtures do not prove live owner API credentials or physical-device behavior. Native and hosted results belong to the exact tested commit recorded in the pull request.
